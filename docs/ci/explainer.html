What is this page?

Nostos's code lives on GitHub, where anyone can read it. Before any change is accepted, GitHub's own computers rebuild the whole project and run every safety check on it. This page explains that safety net: what happens to a change, what gets checked, and the trade-offs chosen on purpose.

Curious how it works under the hood? Flip the switch to — no page reload, nothing to install.

What happens when someone changes the code?

  1. Work happens on a side copy. Each task gets its own copy of the project, so unfinished work never mixes with the finished main version.
    the machinery: a git worktree, make worktree NAME=…
  2. The developer runs the checks first. One command runs the same checks GitHub will run, so problems show up on the laptop instead of later.
    the machinery: scripts/check.sh
  3. The change is proposed, with a label. Every proposal names the pipeline step it belongs to, such as [arxa-builder], and says what is now true.
    the machinery: a pull request
  4. GitHub's computers check it. Eight checks must pass. A ninth only gives a reminder about the label.
    the machinery: the ci.yml and pr.yml workflows
  5. Only a green change joins the main version. The merge happens on GitHub, never on someone's laptop, and nobody uploads straight to the main version.
    the machinery: merge on GitHub; a pre-push guard refuses main
  6. Releases are a separate, deliberate step. Joining the main version publishes nothing. A release happens only when someone tags a version number.
    the machinery: release.yml on a v* tag

The safety checks, in plain words

  • Tidy history. Every change note starts with a standard label such as “fix:” or “feat:”.
    commits · required
  • Code quality and tests. The code is neatly formatted, has no warnings, and every automated test passes.
    lint-test · required
  • A real database. Syncing from a real Postgres database works from end to end.
    e2e-pg · required
  • Licences and security. Every outside building block has an allowed licence and no known security hole.
    deny · required
  • App kits really talk. The Rust, Node, .NET and Tauri kits actually send and receive data.
    sdk-e2e · required
  • Flutter kit and demo app. The Flutter kit and the atlet reference app build and pass their tests on a Mac.
    flutter · required
  • Speed smoke test. A small benchmark still runs. It only proves nothing broke; the headline speed numbers are measured separately.
    benchmark · required
  • JavaScript kits. The React Native and Capacitor kits still type-check.
    sdk-typecheck · required
  • Labelled proposal. The proposal title carries its pipeline label. A missing label blocks the proposal.
    pr-title · required

Good to knowhonest trade-offs, on purpose

  • Public project, GitHub's computers. Anyone can propose a change, so the checks never run on our own machines.
    GitHub-hosted runners (row 8)
  • The main-version lock is not on yet. It is switched on after the project history has been replayed into its new home. Until then, a guard on each laptop refuses direct uploads to the main version.
    branch protection, prepared in docs/ci/setup.md; the pre-push hook
  • The label check only reminds, for now. It becomes a hard rule once the habit has settled in.
    row 5
  • A laptop missing a tool skips that check. It says so in one line. GitHub always runs everything.
    green by absence (row 4)
  • Nothing ships by itself. Merging never deploys. Releases are built only from version tags.
    row 11

Every job has a local twin, scripts/check.sh <area>, with the same name and the same steps; the commits and pr-title jobs run it verbatim. Every job has a timeout. Both workflows carry concurrency + cancel-in-progress and a read-only token. “required” = listed in the protection PUT prepared in docs/ci/setup.md, applied after the retro replay.

The guardrail, as a testeach line is checkable, not aspirational

  • The main clone is on main; git worktree list shows one entry per open task under .worktrees/.
  • make hooks sets core.hooksPath to scripts/hooks, and git push origin HEAD:main is refused. ARXA_ALLOW_MAIN_PUSH=1 is for the retro replay only.
  • Every job has timeout-minutes; ci.yml and pr.yml carry concurrency + cancel-in-progress.
  • Job-per-area: every CI job has a same-named scripts/check.sh area; there is no bare gates job.
  • The commit gate excludes merge commits (git rev-list --no-merges).
  • The CI token is read-only: top-level permissions: contents: read.
  • The title check reads its allowlist from the tag map in decisions.md and warns when the PR template's copy drifts.
  • Protection contexts = the real job names. Prepared, not yet applied: the user runs the PUT after the retro replay. Rename a job → edit the list and re-run the PUT.
  • The PR-title check is required (row 5); add its context to the protection PUT in setup.md.
  • A queued job is never fixed by changing code. On GitHub-hosted runners, queued means GitHub capacity.
