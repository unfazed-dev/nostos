Nostos × Flutter — direct mode

Your app already has the data.
Nostos just keeps every copy honest.

A 5-minute, click-it-yourself explanation of how a Flutter app syncs with Postgres — with no server of yours in the middle — including what happens when the Wi-Fi dies, and what happens when a phone stays dead for a week.

1. The 10-second version

Most apps work like a vending machine: you press a button, it phones a server, you wait, you get data. No signal? No app.

Nostos flips it. Your phone keeps its own little database (SQLite) right there on the device. Your Flutter UI reads from that — instantly, always, offline or not. Nostos's job is boring and important: keep that local copy and the big database agreeing with each other, and never lose a change.

In direct mode — the default when your database is Supabase, or anything else running PostgREST and Realtime — there is nothing for you to run. No Nostos server, no VPS, no Docker. The phone talks to Postgres itself, through the HTTP API the database already has.

2. Meet the cast

🗄️
PostgresThe big fridge in the kitchen. The real, permanent data lives here. On Supabase it already speaks HTTP, so a phone can talk to it without anything in between.
📒
The change logA plain table — cairn.changes. A trigger appends to it inside the same transaction as your write, so a change and the note about it are never out of step.
🔔
RealtimeThe doorbell. It rings "something changed for you" — it doesn't carry the data. The phone hears the ring and goes and reads the log itself.
📱
SQLite + outboxYour snack drawer. Your rows, plus a queue of your own writes that haven't reached the fridge yet.
🎨
FlutterThe face. It never waits on the network. It only ever reads the snack drawer — that's the whole trick.

        4. So what's the Flutter side look like?

        Honestly? About ten lines, and none of them mention a server. Click any line to see what it really does.

        final nostos = await Nostos.direct(
  supabaseUrl: 'https://<ref>.supabase.co', anonKey: '<publishable key>',
  scope: 'sub:' + session.user.id, token: session.accessToken);

await nostos.subscribe('todos');

nostos.watch('todos').listen((rows) {
  setState(() => _todos = rows);   // your UI, updated
});

await nostos.write('todos', op: 'upsert', pk: id, payload: {'title': 'buy milk'});

        5. Three things people get wrong

        “I need a server. And Docker.” — Not in direct mode. The phone talks to Postgres through the HTTP API Supabase already gives you. What you deploy is SQL: nostos link --mode direct writes it, you apply it once, and nostos doctor --mode direct tells you whether the deployed schema, the grants and the policies actually match.
        “No internet means no app.” — Wrong, and this is the whole point. Writes land on your phone's disk first and return immediately. The UI never waits for Wi-Fi. The change sits in an outbox until the world comes back, then leaves in order.
        “A phone that's been off for a month silently loses rows.” — No. The log is kept for a retention window and pruned behind it. A phone resuming from a horizon that's been pruned away gets a 410 Gone — not a short answer it would mistake for "nothing changed" — and re-reads the whole picture with cairn_snapshot(). Loud, and it heals itself. (Try 🧹 Prune while a phone is in airplane mode.)

        6. What you'd actually need to run this

        ① A Supabase projector anything else serving PostgREST + Realtime over your Postgres. Nothing to install on it.
        ② One SQL file, applied oncenostos link --mode direct generates .nostos/direct.sql — the log table, the triggers, the RLS policies, and the cairn_pull / cairn_snapshot functions. Re-runnable.
        ③ Your Flutter appflutter pub add nostos_flutter, then those ten lines. Nothing else runs anywhere.

        Heads-up: Nostos is alpha right now — great for learning and side projects, not for your bank.

        7. When you'd still want the server

        Direct mode is the default, not the only mode. nostos-server is still there, and there are two honest reasons to reach for it.

        Your backendModeWhy
        Supabase, or any PostgREST + RealtimedirectThere is no process for you to operate. The anon key plus row-level security is the whole trust story.
        Plain Postgres you host yourselfserverDirect mode has nothing to talk to — no HTTP API, no doorbell. nostos-server reads Postgres' replication stream and fans changes out over WebSockets itself.

        The other reason is scale: one Rust process fanning out to many clients does work a per-device HTTP pull cannot. That is a measured claim with rules attached — see docs/BENCHMARK-METHODOLOGY.md — and it is not the claim being made on this page.

        One thing that is genuinely different: in server mode the process must stay awake. It holds a Postgres replication slot, and while it sleeps Postgres piles up WAL for it. Direct mode has no slot to hold — the log is an ordinary table with an ordinary retention window, which is why a phone can be away for a week and the failure is a 410 rather than a hole.
