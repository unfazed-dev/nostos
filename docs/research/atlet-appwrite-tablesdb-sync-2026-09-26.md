# Atlet on Appwrite TablesDB: sync feasibility (2026-09-26)

## Decision

**Conditional, not yet proven.** TablesDB can store Atlet rows, enforce per-user/team permissions, commit multi-row writes atomically, and send live change and push notifications. Its documented Realtime API is a live subscription, with no documented persistent offset or missed-event replay. The [offline-sync guide](https://appwrite.io/docs/products/databases/tablesdb/offline) describes a push/pull pattern, but does not supply a change-log protocol. Therefore, a Nostos adapter **cannot equate Realtime events or `$updatedAt` queries with lossless offline catch-up**. Appwrite Cloud proof is required before this can be promised to users. This is an inference from the cited API contracts, not an Appwrite statement that a reliable adapter is impossible.

## Contracts that matter

| Area | Current first-party contract | Nostos implication |
| --- | --- | --- |
| Snapshot and paging | `listRows` offers filters, ordering, and cursor paging; default is 25 rows. Appwrite warns offset paging can miss/duplicate entries in changing tables. Cached list results can be stale until TTL expires. [Queries](https://appwrite.io/docs/products/databases/tablesdb/queries), [pagination](https://appwrite.io/docs/products/databases/tablesdb/pagination), [rows](https://appwrite.io/docs/products/databases/tablesdb/rows) | Page a full snapshot with a stable key and `ttl=0`; test writes during paging. The docs do **not** establish a consistent cross-table snapshot or a matching high-water mark. A fetch-then-subscribe or subscribe-then-fetch handoff must be proved or repaired by reconciliation. |
| Incremental events | Realtime delivers changes to *connected* WebSocket subscribers, including row create/update/delete channels. Subscriptions are permission-scoped; Server SDKs with API keys have no Realtime access. A new user session needs a new subscription; expired sessions stop receiving events. No replay cursor is documented. [Realtime](https://appwrite.io/docs/apis/realtime), [channels](https://appwrite.io/docs/apis/realtime/channels), [auth](https://appwrite.io/docs/apis/realtime/authentication) | Use Realtime as a wake-up hint only. A persisted, permission-filtered change feed with a resume cursor is needed for offline periods, crashes, and missed notifications. |
| Deletes | Realtime has delete events; `deleteRow` removes rows from normal lists. [Channels](https://appwrite.io/docs/apis/realtime/channels), [Rows API](https://appwrite.io/docs/references/cloud/server-nodejs/tablesDB) | Offline clients cannot discover a deletion by listing current rows or querying `$updatedAt`. Persist tombstones in the durable feed, or perform a complete authoritative reconciliation that evicts absent rows. Test permission revocation separately: lack of read access also makes a row disappear. |
| Transaction ordering | TablesDB stages create/update/upsert/delete/atomic numeric operations and commits them atomically in order with conflict detection. Plans cap operations at 100/1,000/2,500 per transaction (Free/Pro/Scale). [Transactions](https://appwrite.io/docs/products/databases/tablesdb/transactions) | A proposed journal row and its data mutation should commit in the **same** TablesDB transaction. A globally monotonic, commit-safe cursor and multi-table snapshot boundary are **unproven**. Stage-time IDs, wall-clock timestamps, and raw Realtime arrival order do not establish commit order. Probe transaction read-your-writes and concurrent commits on Appwrite Cloud before choosing a cursor algorithm. |
| Row sequence | Every inserted row has a system `$sequence` string used for row ordering; Appwrite presents it as a per-table insert sequence. [Row model](https://appwrite.io/docs/references/cloud/models/row), [first-party sequence guide](https://appwrite.io/blog/post/track-document-order-with-sequence) | A dedicated journal table might use `$sequence` as a cursor, but the docs do not guarantee that sequence assignment follows **commit** order when concurrent transactions stage journal inserts. It also does not record updates/deletes unless separate journal rows are appended. Cloud concurrency proof remains mandatory. |
| Timestamps | `$updatedAt` is ISO 8601; Server SDKs with API keys may override it. [Queries](https://appwrite.io/docs/products/databases/tablesdb/queries), [timestamp overrides](https://appwrite.io/docs/products/databases/tablesdb/timestamp-overrides) | Timestamp-only catch-up is unsafe for hard deletes, equal timestamps, backdated writes, and concurrent commits. A `(timestamp, row ID)` tie-breaker only solves ties, not those other gaps. |
| Authorization | Table permissions apply to every row; row permissions require Row Security. Appwrite grants access if either level grants it. `Role.user`, team roles, and labels are available. Client sessions respect permissions; API keys bypass user permissions, while a Server SDK with a user JWT acts under that user's permissions. JWTs expire after 15 minutes or session deletion. [Database permissions](https://appwrite.io/docs/products/databases/tablesdb/permissions), [roles](https://appwrite.io/docs/advanced/security/permissions), [JWT](https://appwrite.io/docs/products/auth/jwt), [accounts](https://appwrite.io/docs/products/auth/accounts) | Put Atlet admin in a restricted team/role; products and orders can be shared according to that role, training sessions stay `Role.user(owner)` private. Never expose an API key in any app or Rust test artifact. Server-mode reads must use/verify the caller's identity, not return API-key-wide rows. Re-snapshot/evict on role or session changes. |
| User admin | Users API is server-side/API-key-only; Account API is for client sign-in. Team owners manage membership; team roles can gate resources. [Accounts](https://appwrite.io/docs/products/auth/accounts), [teams](https://appwrite.io/docs/products/auth/teams) | The visual admin UI needs a privileged backend operation with independent admin authorization. A user's team role is not a license to bundle an API key in the app. |
| Push | Messaging supports APNs for Apple and FCM for Android/Apple/web, with registered per-device targets and provider credentials. Appwrite calls APNs best-effort; Messaging says push may be missed. [Push setup](https://appwrite.io/docs/products/messaging/send-push-notifications), [APNs](https://appwrite.io/docs/products/messaging/apns), [FCM](https://appwrite.io/docs/products/messaging/fcm), [targets](https://appwrite.io/docs/products/messaging/targets), [messages](https://appwrite.io/docs/products/messaging/messages) | Test receipt on physical devices/browsers, but treat push strictly as a wake-up signal. On wake, foreground, and reconnect, pull the durable feed. Do not advance a sync cursor because a notification was sent or displayed. |
| Events and limits | Appwrite Function event triggers are asynchronous queue jobs; synchronous Functions have a 30-second hard timeout. Client requests can receive 429; additional abuse limits can apply to aggressive polling/high concurrency. API-key Server SDK requests bypass ordinary route limits, not necessarily all service protections. [Function execution](https://appwrite.io/docs/products/functions/execute), [rate limits](https://appwrite.io/docs/advanced/security/rate-limits) | A post-write Function event is unsuitable as the *only* journal writer: the original row commit can precede or outlive its journal entry. Coalesce doorbells, back off on 429, bound pulls, and measure hosted pressure within plan limits. Appwrite Cloud supports a [Rust Functions runtime](https://appwrite.io/changelog/entry/2026-05-04), if a hosted sync endpoint is chosen. |

## Fit with Nostos today

[ADR-0023 D4](../adr/0023-dot-nostos-project-directory-and-backend-adapters.md) calls Appwrite **post-v1** and sketches Realtime as the change source and REST as write-back. That sketch is insufficient for Nostos's current correctness contract: [direct-mode generated SQL](../../crates/nostos-cli/src/direct.rs) writes a change row in the Postgres transaction, and [the core pull protocol](../../crates/nostos-core/src/pull.rs) persists a safe `xid8` horizon after local apply. [The native client](../../crates/nostos-client/src/postgrest.rs) reports pruned history as 410 and requires re-snapshot. The [CLI](../../crates/nostos-cli/src/commands/link.rs) rejects `appwrite`; existing Supabase direct mode calls PostgREST RPCs, so changing a config label cannot make TablesDB work.

**Suggested spike, not a committed design:** use a small Rust hosted sync endpoint (Appwrite Function or Nostos adapter service) for both pull and write-back. It must authenticate the Appwrite user, enforce row visibility, own *all* synced writes (including admin writes), atomically record tombstones/change rows with data mutations, expose a tested monotonic resume cursor, and detect retention gaps for full re-snapshot. Appwrite's TablesDB transactions make the atomic write pair plausible; the global cursor, snapshot boundary, permission-change eviction, and external Console/SDK writes remain open. If “direct mode” means *no Nostos-operated server*, a hosted Appwrite Function may fit; if it means *client directly calls TablesDB only*, this approach changes that contract and needs explicit approval. A generic Nostos server-mode facade is separately plausible but still needs the durable change source. Appwrite and Supabase are distinct cloud databases; one Atlet app can run the **same scenarios and schema** against each, but they cannot literally share one database without a separate bridge.

## Hosted-cloud feasibility gates before implementation promise

1. On an isolated Appwrite Cloud project, test a dedicated journal table's `$sequence`, or a transactionally incremented counter, as a cursor. Prove that data+journal commit atomically and the cursor follows **commit** order under many writers. Inject conflicts and process kills; reject any hole or out-of-order visibility.
2. Seed more than one page, mutate and delete rows while a fresh device snapshots, disconnect it for many writes, then resume. Assert exact convergence across tables, no missing deletes, and no duplicate user-visible effects.
3. Attempt writes through the app, Console, direct TablesDB SDK, and admin UI. Either journal every path or explicitly prohibit/bypass-proof uninstrumented writes; a post-commit event handler alone cannot certify same-transaction capture.
4. Sign in as admin and two customers. Verify products/orders visibility, private sessions, denied writes, role revocation, local cache eviction, JWT expiry/refresh, and Realtime re-subscription.
5. Verify APNs/FCM/web notification receipt with real targets, then drop notifications and prove sync still converges. Test retries/429 and retention expiry with snapshot recovery.

**Stop condition:** Until gates 1–3 pass, label Appwrite TablesDB integration experimental and do not claim the same Nostos offline guarantees as the Postgres/Supabase path.

## Repeatable cloud tests across Atlet SDKs

The shared-database requirement applies **within each provider**: every SDK's Atlet app and test users point at one hosted Supabase staging project, and later at one separate hosted Appwrite project. Supabase's [deployment guidance](https://supabase.com/docs/guides/deployment) recommends separate production and staging environments; its preview branches carry schema without production data. Each test run should own a unique fixture namespace and clean up its own rows/users, so one SDK's stress run cannot corrupt another's assertions. Keep cloud secrets in [GitHub environment secrets](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments), never in app binaries or test reports. These are proposed harness choices, not existing repo behavior.

A Rust CLI can own the common scenario contract and expose `--sdk`, `--backend`, `--mode`, and `--suite smoke|e2e|pressure|stress`; one Rust entry point per SDK can call that shared crate. This meets the Rust-script requirement while invoking the platform's real UI driver: Flutter [integration tests](https://docs.flutter.dev/testing/integration-tests) for mobile/web, [Playwright projects](https://playwright.dev/docs/test-projects) for browser apps, and Tauri's [WebDriverIO service](https://v2.tauri.app/develop/tests/webdriver/) for desktop. A Rust-only HTTP test cannot establish that the visual app, local SQLite/IndexedDB, background lifecycle, or push registration works. Run the same admin/two-customer fixture through every SDK against the same provider project and assert cross-client convergence after offline edits, reconnect, deletes, authorization changes, and process restarts.

Keep fast deterministic checks in the required PR gate. Expose hosted smoke/E2E and bounded pressure/stress as separately selectable [manual GitHub workflow inputs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), with explicit run IDs, concurrency limits, and stored results. This is a proposed CI shape for discussion; it preserves a one-command local invocation for any SDK while avoiding unbounded cloud load on every PR. Test push on real registered devices/browsers and verify data by pulling after notification loss, since Appwrite's [push docs](https://appwrite.io/docs/products/messaging/send-push-notifications) do not promise delivery.
