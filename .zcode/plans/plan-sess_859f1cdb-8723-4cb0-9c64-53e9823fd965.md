## Root cause (Phase 1 complete — verified, not guessed)

**Bug:** `watch()` in `sdk/nostos_flutter/rust/src/api/nostos.rs` emits its initial snapshot (line 310) **before** creating its change-broadcast receiver (line 315). When a snapshot-on-subscribe `apply_batch` commits during that window, its change broadcast is missed — the channel is a `tokio::broadcast` with **no replay buffer** (asserted by test `subscribe_changes_receiver_starts_with_no_pending_notifications`, client.rs:1037). The watch then never re-snapshots, so the UI renders "No providers yet." until the next *external* change arrives.

**Evidence chain:**
- Your screenshot: "connected" badge + "No providers yet." empty state.
- SQLite ground truth (queried directly via `sqlite3`): `cairn_data` had 12–13 rows; the `providers` view returned 3–4 rows with real typed JSON. So the sync engine, storage, and views are all correct — data was on disk.
- Rust FFI `watch()` (nostos.rs:310 vs 315): the ordering that creates the race.
- `nostos-client` (client.rs:1037): broadcast has no replay → a send before `subscribe()` is permanently lost to that receiver.
- Intermittency explained: the race window is small, so most runs win it (mine did, repeatedly) — but under timing pressure (cold start, snapshot arriving during the gap) it loses, producing your empty screen.

## Fix (Phase 4 — minimal, root-cause)

**Single change:** in `sdk/nostos_flutter/rust/src/api/nostos.rs`, `watch()`, create the `subscribe_changes()` receiver **before** calling `emit_snapshot()`. Swap lines 310 and 315 (and move the comment accordingly).

```rust
// Create the change receiver BEFORE the initial snapshot so a commit
// landing during (or just before) emit is not lost. The broadcast channel
// has no replay buffer (see subscribe_changes_receiver_starts_with_no_pending_notifications),
// so receiver-after-emit can miss the snapshot-on-subscribe tick → empty UI.
let mut changes = session.client.subscribe_changes();

// Immediate snapshot of durable rows (reads live disk via rows_for, no cache).
emit_snapshot(&session.client, &table, &rows_sink).await;
```

**Why this is complete (not partial):**
- Snapshot already applied before `watch()` called at all → `emit_snapshot` reads live disk (which has the rows) → emits correctly. (Never broken.)
- Snapshot applies after receiver created → receiver catches the broadcast → re-snapshot. (Handled.)
- Snapshot applies between the two lines → **eliminated**: receiver now exists before emit. (The fix.)
- Pre-`watch()` snapshot + later change → emit reads disk (rows present) + receiver catches later changes. (Handled.)

No `nostos-core`/data-plane change. No `wire.rs` change. Matches ADR-0009 (one session, one sink). `resume()` is unaffected (it doesn't touch watch pumps).
